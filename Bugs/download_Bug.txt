# 🧠 What’s really happening

Even though you already ran:

```bash
--appimage-extract
```

Resolve 21 uses a **hybrid AppImage-style installer** that still tries to:

* mount squashfs via FUSE at runtime
* or spawn internal AppImage runtime logic

But your container:

* has **no FUSE device passed through**
* likely has **no `CAP_SYS_ADMIN` for mounting**
* and is running under **containerd + overlayfs isolation**

So:

> ❗ Even extraction mode is partially broken in some modern AppImage runtimes when they detect “unsupported environment”

That’s why you see a “fake extraction” (`squashfs-root` with only `.DirIcon`).

---

# 🔍 Why your extraction produced almost nothing

This is the key clue:

```text
squashfs-root
└── .DirIcon only
```

That means:

### 👉 The embedded SquashFS payload was NEVER mounted or unpacked

So the installer is not actually being extracted — only metadata is visible.

---

# 💡 The real issue (important)

You are in a container with:

### Missing kernel-level features:

* ❌ `/dev/fuse`
* ❌ mount namespace permissions
* ❌ privileged loop mounts
* ❌ likely restricted `unshare()` capabilities

So AppImage-based installers that depend on runtime mounting will **always fail here unless you change runtime config**.

# 🛠️ Your real options (choose one)

## ✅ Option 1 — Proper fix (recommended for your platform testing)

Expose FUSE into the container:

On host / container runtime:

### Docker/containerd config needs:

```bash
--device /dev/fuse
--cap-add SYS_ADMIN
--security-opt apparmor=unconfined
```

and ensure kernel module:

```bash
modprobe fuse
```

Then inside container:

```bash
apt install -y fuse3 libfuse2
```

✔ This makes AppImage behave normally
✔ This is the “real world desktop cloud fix”
✔ This validates your Selkies + HAMI stack properly
